Project controls

Authority, ownership, evidence, naming, and change rules for producing the weekly electrical specification without prematurely implementing circuits.

01 · Authority

Inputs have an explicit order of precedence

1 · User decisionsThe current conversation and the sixteen locked decisions in preflight-decisions.html.
2 · Electrical sourceOperational Amplifiers: Theory and Practice by James K. Roberge. Exact figures, equations, and prose must be read before adaptation.
3 · Project narrativecapstone.html, interpreted as the pedagogical sequence rather than independent proof of electrical correctness.
4 · Execution contractimplementation-plan.html, which controls phases, gates, outputs, and verification.
5 · Prior experimentsExisting schematics*.html, generators, figures, and checker results are evidence of attempted presentation methods, not authoritative connectivity.
Conflict rule

If two authorities conflict, the conflict is entered in the issue ledger and escalated. A drawing or netlist must not silently resolve it.

03 · Specification schema

Every weekly state uses the same evidence structure

Identity and purpose

Week ID, end-state title, active experiment, learning objective, and configuration variants.

Cumulative state

Inherited modules, active modules, retained-inactive modules, removals, replacements, and explicit delta.

Source evidence

Roberge section, figure, PDF page, source statement, and confidence or ambiguity.

Electrical boundary

Components or modules, stable proposed IDs, pins, named nets, hierarchy, and configuration-specific connections.

Parameters and values

Symbolic quantities, recommended candidates, tolerance/rating constraints, and evidence label.

Practical additions

Construction details added beyond the textbook, rationale, and effect on topology or behavior.

Verification

Ideal and realistic SPICE targets, expected measurements, analytical checks, and valid non-operational outcomes.

Presentation

Main/detail sheet recommendation, active/inactive styling, required annotations, and deferred physical patch routing.

Historical and modern

LM301A primary baseline, 741-class alternative notes, and modern ±15 V substitutions where appropriate.

Issues and decisions

Unresolved assumptions, source conflicts, missing data, safety questions, and Gate 0 decisions.

04 · Evidence vocabulary

Claims cannot masquerade as verified values

VerifiedDirectly supported by a cited Roberge figure, equation, table, or explicit project decision.
DerivedCalculated from verified assumptions. The formula, inputs, units, and dependency must be shown.
ProposedAn engineering recommendation requiring review, simulation, or measurement before release.
TBDMissing or unresolved. A TBD is visible and blocks the relevant acceptance gate; it is never filled by aesthetic inference.
DeferredExplicitly excluded from the first implementation and tied to D-01, D-02, D-03, or D-04.

05 · Stable naming

Identifiers survive layout and week changes

  • Week states: W00 through W13.
  • Configuration variants use the integration register. Campaigns such as Week 13 fixed-lag, load-capacitance, and one-pole work are split into one canonical ID per distinct electrical graph.
  • Physical module, socket, occupant, component, and net IDs are governed by gate-0-integration-register.html. Range-draft aliases are retired at integration.
  • Physical component IDs remain stable once installed. A replacement receives a new ID; removal is an explicit state change.
  • Named nets express electrical function, not drawing coordinates. Physical patch-cord paths are deferred, but the nets they realize remain explicit.
  • Main/detail sheet boundaries expose named pins and must match pin-for-pin.

06 · Ownership and file rules

Parallel research, single integration owner

  • Week 0–4, Week 5–9, and Week 10–13 researchers own separate draft files under drafts/.
  • The primary agent alone owns the integrated weekly specification, global identity/state register, cross-week transitions, and Gate 0 issue ledger.
  • Existing source, HTML, generator, figure, and test files are read-only during Phase 0/1.
  • Later generated SVG, SPICE, values, and reports will be outputs; direct hand edits will be prohibited.
  • Every durable artifact must say whether it is authoritative, draft, generated, evidence, or deferred.
